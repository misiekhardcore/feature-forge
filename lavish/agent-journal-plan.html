1 · Why the bug happens

Root cause: agents are destroyed after execution → absent from the supervisor on reopen; the persisted logs never record pass/fail; the reload fallback ensureStaleEntry guesses passed: false.
FileContentWhat it's forProblems
{id}.streamformatted display lines (filtered)"last line" in the list viewhuman-only, lossy, can't rebuild state
{id}.events.jsonlraw pi JsonAgentSessionEvent (message_*, tool_execution_*, agent_start/end…)detail-view historypi-level only — agent_end has no pass/fail; message_update deltas; rotated at 50k lines
{id}.messages.jsonlextracted finalized AgentMessageconversation cachethird ad-hoc schema, duplicates message data
The authoritative signal — feature-forge:agent-done with passed + summary (emitAgentDone) — is never written to disk. That is the "doesn't store the status" half of the problem; ensureStaleEntry hardcoding passed: false is the "loading it incorrectly" half.

2 · How oh-my-pi does it

OMP (a pi fork) models both problems structurally instead of with ad-hoc files and regex:

Persistence — one typed session stream

  • SessionEntry union: message | custom_message | compaction | branch_summary | model_change | thinking_level_change, each with id / parentId / timestamp
  • Each subagent gets its own session file (sessionFile in lifecycle payloads) in the same format
  • Append-only, replayable — state is derived from the stream, never guessed

Responses — schema-first

  • omptype: an ArkType-compatible schema library — type({ "status?": "'pending' | 'running' | 'completed' | 'failed' | 'aborted'", … })
  • Tools declare schemas; results are asserted/validated against them
  • SubagentLifecyclePayload { status: started|completed|failed|aborted, sessionFile } — status is a first-class typed field
  • AgentProgress: rich snapshot — status, currentTool, tokens, cost, duration

3 · Proposed design

A · One typed agent journal

Replace the 3 files with {streamDir}/{agentId}.journal.jsonl — append-only, discriminated union, status first-class. Reopen = replay, not guess.

{"type":"lifecycle","phase":"started","ts":"…"}
{"type":"stream","line":"⟳ builder (build) started","ts":"…"}
{"type":"message","message":{…},"ts":"…"}
{"type":"tool","toolName":"read","result":…,"isError":false,"ts":"…"}
{"type":"lifecycle","phase":"done","passed":true,"summary":"ok","ts":"…"}  ← the fix

B · Schema-validated responses

Per-instruction output schema (TypeBox — same machinery pi already uses for tool args). Parse → validate → retry with specific errors instead of "append the JSON block".

// flow.json — declared contract, typed details
"agent": { "id": "builder", "outputSchema": {
  "passed": "boolean", "summary": "string",
  "details": { "files": ["string"], "rounds": "integer" } } }

// executor — one validate call, no regex guessing
const out = extractJsonBlock(raw);
const errors = [...Value.Errors(schema, out)];
if (errors.length) → retry(prompt + errors)

3B · TypeBox vs ArkType (omptype) — the D3 question

They express the same things; the difference is authoring style, interop, and tooling. ArkType's string DSL is sugar over what TypeBox already does programmatically — everything ArkType can express, TypeBox can express:

ArkType / omptypeTypeBox equivalent (JSON Schema)
type("'feat' | 'fix' | 'refactor'")Type.Union([Type.Literal("feat"), Type.Literal("fix"), Type.Literal("refactor")]) (a small enumLiteral() helper makes it one line)
type({ text: "string", "x?": "boolean" })Type.Object({ text: Type.String(), x: Type.Optional(Type.Boolean()) })
type("string.integer >= 0")Type.Integer({ minimum: 0 })
type("boolean = true")Type.Boolean({ default: true })

Why ArkType is nice

  • Terser authoring — a compact string DSL reads well in a declarative flow.json
  • Blazing validation speed (irrelevant at our low output frequency)
  • Excellent static inference ergonomics (schema is the type)

Why TypeBox wins for us

  • Already in the stack — tool params (buildParamsSchema) and FlowDefinitionSchema are TypeBox; an outputSchema nests naturally
  • JSON Schema interop — provider structured outputs (response_format/Anthropic tool-shaped JSON) take JSON Schema; ArkType/omptype is not JSON Schema
  • Value.Errors / Compile / Convert — the exact validation + error-reporting machinery pi already uses for tool args
  • No new runtime dependency, no divergent schema dialect in the repo

What "verbose" means concretely — the same schema two ways

Raw JSON Schema in flow.json (TypeBox output)

"outputSchema": {
  "type": "object",
  "properties": {
    "passed": { "type": "boolean" },
    "summary": { "type": "string" },
    "details": {
      "type": "object",
      "properties": {
        "files": { "type": "array", "items": { "type": "string" } },
        "status": { "enum": ["pending","running",
                            "completed","failed"] }
      },
      "required": ["status"]
    }
  },
  "required": ["passed","summary","details"],
  "additionalProperties": false
}

ArkType-style DSL (as a flow.json string)

"outputSchema": "{
  passed: 'boolean',
  summary: 'string',
  details: {
    files: 'string[]',
    status: 'pending | running | completed | failed'
  }
}"

Same contract, ~4x fewer tokens. That is the entire ArkType pitch.

Mitigations if flow.json authoring hurts: keep schemas TS-side (like the tool schemas — zero flow.json noise, helpers like enumLiteral()), or add a tiny DSL string parsed at flow-load time. All keep the TypeBox enforcement substrate.

D3 revised (user decision): go full ArkType like OMP. Adopt the real arktype package, wrap it in a forge-owned facade, and model the enforcement pipeline on OMP's structured-subagent architecture. TypeBox remains only where the pi platform requires it (tool params, flow validation).

Why the flip is sound: OMP is battle-proven on exactly this pattern — ArkType DSL for authoring, JSON-Schema bridge for providers/wire, strict|permissive validation, schema-error-driven retry. The earlier TypeBox argument (already-in-stack) is real but the DSL ergonomics for hand-authored flow.json and the OMP parity the user wants win. The wrapper keeps arktype out of the rest of the codebase.

Migration / compatibility: existing .stream / .events.jsonl / .messages.jsonl files exist in every user's log dir. Options: one-shot migrate on first prepopulate, read-side fallback to legacy files, or accept history loss. Retention/prune (#230) already covers the directory.

6 · Copy-paste prompt for the quick fix (Phase A)

Fix the stale-agent status rendering bug in feature-forge (~/Projects/feature-forge, main).

Root cause: packages/cli/src/tui/state/AgentViewerState.ts — prepopulateStreamFiles()'s
ensureStaleEntry() creates a disk-derived entry with `passed: false` hardcoded when an
agent has persisted stream files but no live entry. Completed agents are destroyed
after execution (AgentStepExecutor.ts:210), so on overlay reopen the supervisor has no
entry; the disk files (.stream/.events.jsonl/.messages.jsonl) record conversation only,
never pass/fail; the fallback then renders ✗ "failed" via getStatusLabel("done", false).

Fix (behavior-preserving except the bug): in ensureStaleEntry remove the `passed: false`
field — leave passed undefined. Per the documented contract in
AgentDisplayHelpers.buildEntry ("passed spread only when defined — undefined renders
'completed', never 'failed'"), unknown pass/fail must render "completed" (green ✓).

Tests:
- Add/extend a test in packages/cli/src/tui/state/AgentViewerState.test.ts asserting the
  stale entry from prepopulateStreamFiles has status "done" and passed is undefined
  (AgentDisplayHelpers.getEntryPassed(entry) === undefined; getStatusLabel renders
  "completed"). Check no existing test locks passed:false on stale entries.

Validation (repo root): npx tsc --noEmit -p packages/cli; npx vitest run --project cli
src/tui/state/AgentViewerState.test.ts src/tui/display/AgentDisplayHelpers.test.ts;
npx eslint + npx prettier --check on the two touched files.

Non-goals: no changes to the persistence format, wireOverlayEvents, or display-helper
semantics; the agent-journal rework is a separate effort.
